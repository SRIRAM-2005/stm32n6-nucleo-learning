# Day 1 Results: GPIO, UART printf, button polling and EXTI interrupt

**Board:** NUCLEO-N657X0-Q (STM32N657X0H3Q, Cortex-M55)
**Tools:** STM32CubeMX (pin/clock setup), STM32CubeIDE (build/debug), STM32CubeN6 HAL
**Runs from:** internal RAM (AXISRAM2), development boot mode

---

## Goal

Get a first program running on a new and unfamiliar MCU, and understand every layer
between power-on and a button press:

- how the STM32N6 boots and how the debugger loads code onto it
- how CubeMX turns a pin configuration into C code
- how `printf` reaches the PC
- how a button press travels through the interrupt system to my code

---

## What was done, and why

### 1. Read the board manual (UM3417) before configuring anything
| Function | Pin | From the manual |
|---|---|---|
| Red LED (LD5) | PG10 | **Active low**: ON when the pin is LOW |
| Green LED (LD6) | PG0 | Active low |
| Blue LED (LD7) | PG8 | Active low (used on Day 2) |
| User button (B1) | PC13 | **Active high**: HIGH when pressed |
| Virtual COM port | USART1, PE5 (TX) / PE6 (RX) | Routed to the ST-LINK USB |

**Why:** the code depends on these facts. Without the manual, the LEDs would have been
driven with the wrong polarity, and the button would have had the wrong pull resistor.

### 2. Configured the pins in STM32CubeMX
| Pin | Mode | Settings | Why |
|---|---|---|---|
| PG10, PG0 | GPIO output, push-pull | Initial level **High** | Active-low LEDs start OFF, with no flash at boot |
| PC13 | EXTI, **rising edge** | **Pull-down** | Button is active high; the pull-down stops the pin floating when not pressed |
| PE5 / PE6 | USART1 TX / RX | 115200 8N1 | These are the pins wired to the ST-LINK virtual COM port |
| NVIC | EXTI Line13 enabled | | So a press triggers an interrupt |

**STM32N6-specific:** every pin and USART1 had to be assigned to the
**FSBL runtime context**. Pins left "Free" get no initialisation code generated.

**Mistake caught:** CubeMX first placed USART1 on **PC4 / PF12**. Those pins are not
connected to the ST-LINK, and PF12 is an Ethernet RMII pin on this board. I moved them to
PE5 / PE6 as the manual specifies.
**Lesson:** CubeMX picks any free pins, not the ones the board actually uses. Always
check its choices against the board manual.

### 3. Project structure: FSBL only
The STM32N6 has **no internal flash**. The boot ROM runs first and hands control to a
**First Stage Boot Loader (FSBL)**. For Day 1, only the FSBL project was generated, and
the debugger loads it straight into internal RAM. The secure/non-secure application
projects (AppS / AppNS) were not needed yet.

### 4. Clock configuration (generated by CubeMX)
```
HSI 64 MHz → PLL1 (÷4 ×75) = 1200 MHz → IC1 ÷2 → CPU 600 MHz
```

### 5. Code (only inside the `USER CODE` blocks, so CubeMX regeneration keeps it)
- **`__io_putchar()`** sends each `printf` character over USART1.
- **Three exercises**, selected with `#define DAY1_EXERCISE`:

| Ex | What it does | Why |
|---|---|---|
| 1 | Blink with `HAL_Delay()`, print a counter | Show that blocking delays freeze the CPU |
| 2 | Poll the button, detect the edge in software, debounce, non-blocking LED timing | Learn polling and timestamp-based timing |
| 3 | Button via **EXTI interrupt**: the ISR only sets a `volatile` flag, the main loop does the work | The standard interrupt design pattern |

- **Debounce (50 ms):** a mechanical button bounces and produces several edges per press.
  Edges within 50 ms of the last accepted one are ignored.
- **`Error_Handler()`** blinks the red LED fast, so a failed initialisation is visible.

- The red LED kept blinking during button handling, so the main loop never blocks.

### How a button press reaches my code
```
B1 pressed → PC13 rises 0→1
 → EXTI line 13 detects the edge
 → NVIC jumps to EXTI13_IRQHandler()           (stm32n6xx_it.c, generated)
 → HAL_GPIO_EXTI_IRQHandler() clears the flag
 → HAL_GPIO_EXTI_Rising_Callback()              (my code: debounce, set flag)
 → main loop sees the flag → toggles green LED → printf
```

### How printf reaches the PC
```
printf() → _write() (syscalls.c) → __io_putchar() → HAL_UART_Transmit()
 → USART1 PE5 → ST-LINK (UART-to-USB) → COM13 on the PC
```

## Debugging: "Failed to start GDB server"

The first debug attempts failed. I narrowed the cause down one layer at a time:

| Check | Result |
|---|---|
| Windows sees the board (Device Manager) | ✅ "ST-Link Debug" + "USB Serial Device (COM13)" |
| ST-LINK found by CubeIDE (Scan) | ✅ serial number found |
| ST-LINK firmware | ✅ V3J17M11, newer than the upgrade tool offered |
| Target powered (LD1 5V_PWR) | ✅ ON |
| **Boot mode** | ❌ **cause found** |

**Root cause:** the STM32N6 **keeps its debug port closed in flash boot mode**. It only
opens it in **development boot mode**. The error changed from `(255) Unknown` to
`(4) No device found on target`, which showed the ST-LINK was working but the chip was
not responding.

**Fix:** on this board, **JP2 (BOOT1) on pins [1-2] = development boot**. The boot ROM
confirms it by turning the red LED on **steady**. (The jumper had been moved from the
factory default position, so the manual's default did not match the board.)

**Lesson:** trust what the hardware shows (the steady red LED) over the documented
default, and use changes in error messages to locate the failing layer.

Other issue: `Error opening COM13 (5)` = access denied, because several serial consoles
had been opened on the same port. Only one program can hold a COM port at a time.

## Interview questions answered by this exercise

**Why does Exercise 1 ignore the button?**
Nothing in its loop reads the button, and the CPU spends nearly all its time inside
`HAL_Delay()`, which is a busy-wait. Blocking delays make the system unresponsive.

**Why is `g_button_event` declared `volatile`?**
It is written in an interrupt and read in `main()`. Without `volatile`, the optimiser may
read it once into a register and never check memory again, because nothing in the loop
writes it. `volatile` forces a fresh read from memory every time.

**Why set a flag in the ISR instead of calling `printf` there?**
- ISRs must be short. While one runs, lower-priority interrupts are delayed, and `printf`
  at 115200 baud takes about 87 µs per character.
- `HAL_UART_Transmit` uses `HAL_GetTick()` timeouts. If the ISR priority is equal to or
  higher than SysTick's, the tick cannot advance, and the code can hang forever.
- `printf` is not reentrant. Calling it in both `main()` and an ISR can corrupt its state.

---

## Key takeaways
1. Read the board manual first: pins, LED polarity, button polarity, boot jumpers.
2. On the STM32N6: no internal flash, boot ROM → FSBL, development boot for debugging,
   and pin runtime contexts in CubeMX.
3. Interrupt design: keep ISRs short, share data through `volatile` flags.
4. Debug hardware problems one layer at a time: USB → probe → power → boot mode.
